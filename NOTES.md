# Sill — build notes

Decisions, deviations from the brief, and how each was verified.

## Environment constraint that shaped everything

This machine has the **Command Line Tools, not Xcode**. Consequences:

- **No `.xcodeproj`, no scheme.** The project is a SwiftPM package: `SillCore`
  (all the logic, testable) and `SillApp` (AppKit/SwiftUI). `Scripts/build-app.sh`
  assembles `Sill.app` by hand; `Scripts/make-dmg.sh` wraps it in a disk image.
- **No `swift test`.** The CLT ship no XCTest, and their copy of swift-testing is
  incomplete (`Testing.framework` is present but `lib_TestingInterop.dylib` is
  missing, so any test bundle fails to `dlopen`). The suite is therefore a plain
  executable — `swift run silltests` — with a ~30-line harness in
  `Tests/SillCoreTests/Support.swift` and a runner regenerated by
  `Scripts/gen-test-runner.sh`. Assertions read `expect(...)` instead of
  `#expect(...)`; porting to swift-testing later is mechanical.
- **No Instruments.** Per-frame main-thread work could not be checked in a
  profiler. It was checked instead by measuring what the profiler would be
  looking for: the wave's motion comes entirely from one `CABasicAnimation` per
  sample, and the app's total CPU time was measured over a 10-minute idle window
  (see below).
- **`swift build --arch arm64 --arch x86_64` needs Xcode's xcbuild.** The Intel
  slice is cross-compiled with `-target x86_64-apple-macosx14.0` and `lipo`'d in,
  so the shipped binary is still universal.

## Bugs worth naming

- **The open panel swallowed clicks in mid-air.** Once the panel could open
  anywhere on the desktop, its window spanned everything between the band and
  the panel — and the whole of that window took the mouse. A click on your own
  window in that gap went to Sill and did nothing. The window now reports only
  the band and, while open, the panel as live: `hitTest` returns nil everywhere
  else, so the gap is a hole.
- **Six tiles in a 430pt column.** On a horizontal band the tiles sat in a
  fixed-width group, so the six of them broke their labels across lines and
  truncated every value ("CP U", "1…"). Three columns, in a wider group.
- **A 3,800pt-wide panel.** A horizontal bar took the band's full width, which
  on this display meant a bar wider than most screens and impossible to fit into
  exposed desktop. Capped at 940pt.

- **Two copies could run at once**, each drawing a band on every display and
  each sampling. A second launch now sees the first and exits.
- **A settings observer that crashed the app.** `UserDefaults.didChangeNotification`
  fires for any default registered anywhere in the process — SwiftUI registers
  some while laying out — and Sill rebuilt its windows synchronously on it. The
  panel's own `sizeThatFits` therefore re-entered the rebuild that raised it and
  died on a Swift exclusivity check ("Fatal access conflict"). Now the work is
  coalesced to the next runloop pass and skipped unless a value Sill actually
  uses has changed, compared through `SettingsSnapshot`. It would have crashed
  users at random.

- **The open animation was skipping.** `animator()` on a view unhidden in the
  same pass has no presentation state to animate from, so it snapped — while
  close, animating from a settled state, ran properly. Both directions now use
  explicit `CABasicAnimation`s with computed from/to values. Measured frame by
  frame (`sill --luma` over a burst of screenshots): open runs
  0.87 → 0.53 → 0.29 → 0.25, close runs 0.25 → 0.32 → 0.61 → 0.83 → 0.87.
- **A one-stop gradient paints nothing.** With a single-entry backdrop profile
  the fade mask collapsed to one stop and masked the whole band away — which is
  what left the settings window's colour preview blank. Gradients are padded to
  two stops now, and a flat backdrop expands to a full slice profile so it still
  fades with age.
- **Distributed notifications reach a background app late**, sometimes by
  seconds, which made every animation measurement meaningless until the test
  hooks moved to signals (`SIGUSR1` open/close, `SIGUSR2` hover). Worth knowing
  before trusting any timing measured through `--toggle`.

## The click that did nothing

The panel took "3-5 seconds" to open. It was not slow: instrumented, the whole
path from mouse-down to an open panel is **7ms** (3ms to measure the panel, 4ms
to fill it, process sampling included). The clicks were being *thrown away*.

Two causes, both fixed:

- The window is a background window of a background app, and `NSView` refuses
  the first click into one by default — that click only activates the app.
  `acceptsFirstMouse` now returns true.
- The window is a `NSPanel` with `.nonactivatingPanel` now, rather than a plain
  `NSWindow`, so taking that click never pulls focus off whatever you were
  working in.

A missed `mouseMoved` event could also leave the band deaf until the pointer
moved again, so hit-testing is re-evaluated on every sample tick as a safety net,
and the hot zone is 6pt larger than the band.

Synthesising a click to prove the fix needs Accessibility permission, which this
session does not have, so this one is verified by construction and instrumented
timings rather than by a click.

## Deviations from the brief

0. **The calendar field is gone.** The brief (§7) puts the next calendar event
   in the footer. In practice EventKit prompts for Calendar access on every
   launch until the prompt is answered, which is a permission tax on every user
   for something that is not system load. The code, the EventKit link and the
   usage-description strings are all removed, so the prompt cannot appear at
   all — rather than left in place asking politely. Battery, throughput and the
   band's time span still carry the footer.

1. **Tests are an executable, not `swift test`** — reason above. 73 tests,
   ~4,300 assertions, no warnings, green.
2. **The band is 76pt deep, not 52, and smoothing runs twice, not once.** At
   52pt the envelope pinned against the edges of the band on a busy machine:
   80% and 100% looked the same, which wastes the top of the scale. 76pt with
   an 8pt inset gives 30pt of amplitude either side. The second smoothing pass
   calms the line without moving where a spike sits — tested, not assumed.
3. **The strand weights are 2.2pt and 0.7pt, not 1.5 and 1.0.** The brief's
   pair sits too close together: nine strands of similar weight read as one
   mass. Widening the gap gives the band a hierarchy — the two envelope
   strands are the CPU reading and carry the shape, the seven inner ones are
   the memory fill and read as texture between them. The fill strands gained a
   little opacity (0.42 to 0.52) because a thinner stroke carries less ink.
4. **Gradient direction fixed in one direction for all four edges.** The brief
   says the ramp runs along the time axis and "must flip correctly for each
   edge"; the prototype is inconsistent between vertical and horizontal. Sill
   always puts the *idle* stop at the newest end and the *heavy* stop at the
   oldest, on every edge. `EdgeTests.gradientRunsNewestToOldest` pins it.
5. **The scrolling layer is an ordinary layer, not the mask.** The obvious
   structure — gradient layer masked by the nine strands, animate the mask —
   compiles, and its presentation values animate, but the render server does not
   composite an animated transform on a mask layer: the wave stepped once per
   sample instead of gliding. Measured, not guessed (see "Motion" below). The
   gradient now travels with the bundle inside a scroll layer, which shifts the
   colour ramp by 4pt per sample before resetting — about 0.1% of a 432pt band,
   invisible in practice, and the alternative was a visible 4pt jump every second.
6. **The horizontal bar spreads its groups instead of centring one column.** On a
   3,000pt-wide band, a full-width bar with one stretched process row is unusable
   and a centred column leaves the glass looking empty. Header and tiles sit left,
   processes centre, footer right.
7. **The detail panel is 344pt wide, not 298.** At the brief's width the
   readings had to be set small enough that the panel stopped being glanceable,
   which is the only thing it is for. Tile values are 23pt, their labels 12pt,
   process rows 13.5pt.
8. **Process CPU comes from `proc_pid_rusage` deltas,** with `sysctl(KERN_PROC_ALL)`
   only supplying the pid list. `kinfo_proc.p_pctcpu` is effectively dead on
   modern macOS. Names come from the executable path, because `p_comm` truncates
   at 16 characters ("Claude Helper (R").
9. **A few debug affordances ship in the binary** but do nothing unless asked:
   `--probe`, `--screens`, `--render`, `--shift`, `--toggle`, `--reload`, and the
   `SILL_DEBUG` / `SILL_FORCE_REDUCE_MOTION` / `SILL_FORCE_REDUCE_TRANSPARENCY`
   environment switches. They are how the verification below was done without a
   profiler or a mouse robot.
10. **Screen lock is polled, not trusted to notify.** The screen locked during
   testing and `com.apple.screenIsLocked` never arrived — sampling kept running.
   The notification is still observed, but `CGSessionCopyCurrentDictionary()`'s
   `CGSSessionScreenIsLocked` is now checked before every sample, and a 5-second
   poll runs while suspended so the app notices the screen coming back (there is
   no sample timer left to notice it otherwise).
11. **History seeds from the first real reading** rather than zero, so a fresh
   launch shows a flat band at the current load instead of a fake idle stretch.
   On a wide display the band holds ~750 samples (12 minutes at 1Hz), so seeding
   matters more than it would on a laptop.

## What it does that a menu-bar monitor cannot

A survey of the field (iStat Menus, Stats, MenuMeters, and Orbl, the one other
wallpaper-native app) settled two decisions:

- **No sensors, fans or SMC.** It is the obvious "more features" move and it is
  wrong here: Stats needs a privileged helper installed with admin rights for
  it, and its own README says sensors and Bluetooth account for up to half its
  energy use. Sill installs nothing, asks for no admin, and reads two cheap
  Mach calls a second. That is the product.
- **Lean on placement.** macOS 26 added a privacy control that can hide menu-bar
  items; a wallpaper app is untouched by it. And where a menu-bar readout shows
  a number, a band shows *the last quarter of an hour* — so the features worth
  building are the ones that make that history useful.

Hence:

- **Scrub, with attribution.** Hover anywhere along the band and a chip reads
  back what the machine was doing at that point — "42% cpu · 71% mem · 3m ago"
  — and, if something was eating it then, names it. That is the question a
  spike actually raises, and no wallpaper monitor answers it. Reading the
  process table is the most expensive thing Sill can do, so `SpikeLog` records
  one name only while load is above 55%, at most once every three seconds, into
  a 64-entry ring, and through a second sampler so the panel's own list keeps
  its baseline. The wave was
  already a record; this makes it answerable. The window keeps a transparent
  gutter inboard of the band for the chip to live in, and that gutter stays
  click-through.
- **A band on every display.** One sampler feeds them all — the readings are
  identical, only the styling is per-desktop, because each screen's wallpaper
  is measured separately. Opening the panel on one display closes it on the
  others: two open panels are two copies of one answer.
- **Network split by direction, and disk read/write.** "2.4 down" and "0.3 up"
  answer different questions, and so do read and write. Disk throughput comes
  from `IOBlockStorageDriver`'s own statistics — the same registry route as the
  GPU reading, so still no helper and no admin. Both are panel-only, and a
  counter that goes backwards (an interface disappearing) reports zero rather
  than a nonsense rate. The panel now carries six tiles: two across on the
  card, six across on the bar.
- **GPU, without a helper.** Every rival shows a GPU figure and Sill did not.
  `IOAccelerator`'s own `PerformanceStatistics` gives it for one registry
  lookup — no entitlement, no admin, no privileged helper — and like the
  process list and network it only runs while the band is open.
- **Battery time remaining** beside the percentage, when the system has an
  estimate to give.
- **The panel says how much history is on screen** ("16m shown"), which depends
  on the band's width, the screen, and the sample interval.

## History is a duration, not a sampling rate

"How much time does the band show" is the question a person actually has;
"how often does it sample" is arithmetic they should not have to do. So the
History setting is minutes (1–60, or Auto for what the band's length gives it),
and the sample interval is derived from it: `Span.interval(minutes:samples:)`
divides the wanted duration by the points the band can hold. A 20-minute span
on a 162-point band samples every 7.5 seconds — which also costs less than
sampling every second, so a longer memory is cheaper, not dearer.

Two things fell out of that:

- **The sample rate is no longer a setting.** A slider that is disabled
  whenever History is set is clutter, so it went; History covers it, and Auto
  means a point a second — the brief's default. The value still exists in
  defaults for anyone who wants to set it by hand.
- **A long span averages its window instead of sampling a moment of it.**
  Readings are taken every second whatever the span, and a history point is the
  mean of the window it covers. A band showing half an hour would otherwise
  sample one second in eleven and miss everything between — and the open panel
  would show numbers up to eleven seconds stale. The expensive part (redrawing
  nine paths) still happens only once per history point.

Where the arithmetic cannot be honoured — an hour of history on a very short
band — the interval clamps and `Span.achievedMinutes` says what the band really
holds. The panel already states the real span ("6m shown"), so the claim and the
picture cannot drift apart. Timer slack scales with the interval too: a band
showing an hour has no need of a wakeup accurate to a fifth of a second.

## Two options that had to stay options

Both were asked for as questions — would anyone want this? — and both answers
were yes, with the default left where it was.

- **Behind: None / Dark / Glass.** A plate behind the band. Dark is a flat
  translucent fill and costs nothing — no blur, so nothing underneath has to be
  recomposited. Glass is a real `NSVisualEffectView`, which the brief warns
  against for exactly that reason; it is offered with the cost stated because on
  some wallpapers nothing else works. The interesting part is what it does to
  the colours: with a plate behind the band the wallpaper underneath stops
  mattering, so `BackdropSample.behind(_:)` replaces the measured profile with
  the plate's own tone and the strands go back to their bright ramp instead of
  staying inked for a wallpaper they can no longer see.
- **Fill under the lines.** The area between the two envelope strands, filled
  with the same ramp and faded to nothing at the axis — strongest at the lines,
  gone in the middle, so it reads as depth rather than as a slab. Built from the
  same monotone curve as the strokes, so the fill's edge sits exactly under the
  line rather than near it.

A subtlety worth recording: the glass plate is a view, and a view always draws
above its host view's own layers. The wave therefore moved into its own
`WaveHostView`, with the plate inserted below it. Without that the plate simply
covered the wave — which is what the first build did.

## Opening a panel that lives behind your windows

The band sits just above the desktop icons, which is right for something
ambient — and wrong the moment you click it, because the panel opens behind
whatever window is over that part of the desktop. Lifting it above everything
fixes the visibility and breaks the premise: Sill should not cover the window
you are working in.

So the panel opens into the desktop that is actually exposed.
`CGWindowListCopyWindowInfo` reports other apps' window *bounds* with no
permission at all (only their contents would need Screen Recording), so the
placement scores candidate spots — beside the band, along it, further inboard,
and a coarse grid over the whole screen — by how covered each is, with a
distance penalty so the panel stays near its band when it can.

The panel belongs beside the middle of its band, and that is where it opens
unless that spot is obstructed — then it slides along the band, or one step
further in, and never off to a corner of the screen. An earlier version scored
a grid of spots across the whole display and would open in the far corner
because that happened to be clear; predictable beats clever.

The honest limit: on a screen with no free space, no placement helps. Measured
on the author's desktop, the best spot was still 75% covered. So the rule is
conditional — stay behind when there is room, come forward while open when the
alternative is being invisible — and "Bring forward when opened" in Settings
forces the front behaviour for anyone who prefers it. Either way, a click
anywhere else puts it away.

The wave no longer slides inboard on open: the band stays where it lives and
the panel appears beside it.

## The wave draws two metrics, and you pick which

A download moved nothing: the shape was hard-wired to CPU and the fill to
memory, so the one thing a user was watching for — a transfer — was invisible
unless they opened the panel. Both are now a choice (Settings → Shape, Fill)
between CPU, Memory, GPU, Network and Disk. Defaults are unchanged.

Rates need a scale that percentages do not: 5 MB/s is enormous on hotel wifi
and nothing on a gigabit link.

The first attempt turned each reading into a percentage as it was sampled,
against a remembered peak that decayed. On a running band that was visibly
wrong, and the user caught it: the network envelope kept slamming to full
height and the strands already drawn appeared to move. Two causes. A new
maximum is by definition 100%, so ordinary background chatter redefined full
height every few seconds; and because the scale drifted while the readings sat
in the history, identical traffic was drawn at different heights depending on
when it happened.

Rates are now stored raw, in bytes a second, and scaled only when they are
drawn — the whole visible window against one scale, which is the step above its
busiest moment (2, 5, 10, 20, 50 MB/s and so on, floor 2 MB/s). Snapping to
steps is what keeps the picture still: scaling to the exact maximum would
redraw every strand slightly whenever the busiest moment changed by a few
kilobytes. Measured on the running app afterwards: zero rescales of the drawn
window over 39 consecutive ticks of live traffic. The panel states what full
height currently means ("full band 20.0 MB/s"), because a band with no stated
scale is a decoration.

CPU, memory, network and disk are recorded whether or not they are drawn, so
pointing the wave at one shows the history it already has. GPU is the exception
— see the second pass below.

## Colour means load, not age

The brief (§2) runs the ramp along the time axis. Built that way it says
nothing: on the Load ramp the newest end was always green and the oldest always
red, so "heavy red" only ever meant "a while ago". The user spotted it
immediately. Colour now encodes **load**: each slice of the band is the ramp
read at the CPU figure recorded there (idle up to 45%, mid to 78%, heavy beyond
-- the same thresholds the process bars use), so a spike stays red as it ages
down the band and a quiet stretch stays green. This is a deliberate departure
from the brief's wording, and the reason it is worth the departure is that it
makes the ramp carry information the envelope alone cannot: *when* the machine
was busy, at a glance.

The gradient travels with the strands (it lives inside the scroll layer), so a
red patch stays attached to the samples it belongs to.

### The ramps travel in hue, not just brightness

Once colour carries the load, a ramp made of three shades of one hue says
"darker", not "busier" — Teal and Amber both were. They now move through hue
while keeping their identity:

- **Teal**: mint `#6FE3C0` → cyan `#22B8C6` → ocean `#1E88C7` (162° → 202°)
- **Amber**: gold `#F6D06B` → orange `#ED8F2E` → rust `#D2422A` (44° → 9°)

Their light-backdrop sets follow the same arc in ink. Mono stays monochrome on
purpose — that is what it is for. A test holds the line: every ramp but Mono has
to travel more than 25° of hue from idle to heavy, with the mid stop genuinely
between the two, in both its dark and light sets.

## Content-aware, slice by slice

Adapting to the wallpaper as a whole was not enough: a band that crosses a
bright sky and a dark hillside has no single right answer. `Backdrop` now
measures the wallpaper under the band in 24 slices along its length, and three
things vary per slice:

- **Tone** — the ramp colour for that slice's load is crossfaded between the
  dark-backdrop and light-backdrop stop sets by how light the wallpaper is
  *there*. Dark ink over the bright half, bright strands over the dark half, in
  the same band at the same moment.
- **The contrast hairline** — white under dark strands on a bright stretch,
  near-black under bright ones on a dark stretch, again per slice.
- **The age fade** — its floor rises where the wallpaper is bright, so the old
  end of the band doesn't wash out over a light patch while still receding
  properly over a dark one.

`sill --backdrop` prints the measurement per display, including a sparkline of
the band (`#` dark, `-` mid, `.` light, newest end first). The built-in display
here reads `#################-......` — seventeen dark slices then six bright
ones, which is exactly the case a single global choice cannot serve.

## Length, and the hover hint

- **The band spans the same fraction of the screen on every edge** — 40% by
  default, of the height on left and right and of the width on top and bottom.
  The brief fixed left and right at 432pt, which on a 1,590pt-tall display is a
  third of the edge and reads as an offcut. The fraction is a setting (30–100%),
  so the eighth item in the settings window is a length slider.
- **The chevron sits at the middle of the band** — considered against putting it
  at the live (newest) end and settled on the middle: it is an affordance for
  the whole band, not a marker for the newest sample.
- **A chevron fades in while the pointer is over the band**, pointing the way the
  panel will open — inboard, away from the screen edge — and reversing to point
  back out once it is open, meaning "put it away". It is drawn outside the age
  mask, because it is an affordance rather than data, and it carries the same
  contrast hairline as the strands so it survives a light or busy wallpaper.
  Opacity is all that animates: 0.16s in, 0.22s out, and nothing at all under
  Reduce Motion.

## Readability on real wallpapers

The first build was unusable on a light desktop: pastel strands at 42% opacity
over pale stone read as nothing at all. Three things fixed it, all automatic —
there is no new setting, and the brief's seven preferences are unchanged.

1. **The backdrop is measured, not assumed.** `Backdrop` reads the wallpaper
   *file* for the chosen display (`NSWorkspace.desktopImageURL`), crops the part
   that sits under the band, and returns its mean luminance — weighted toward the
   lighter quartile, since the bright half is the half that defeats a pale
   strand — plus the spread between light and dark, which is how "busy" is
   measured. No screen capture, so no Screen Recording permission, and the result
   is cached per wallpaper file and modification date.
2. **Each ramp has a second set of stops for light backdrops**, crossfaded in as
   the wallpaper lightens (`ColorRamp.lightBackdropStops`). They are picked, not
   derived: arithmetically darkening #FFC53D gives olive, so Load's mid stop
   moves to burnt amber (#A65E06) instead. Mono flips from white to ink — white
   on white is not a colour scheme. Opacity, stroke width and the fade floor all
   rise with lightness as well (inner strands 0.42 → 0.68, outer 1.5 → 1.9pt).
3. **A contrast hairline under each strand**, in the backdrop's opposite tone,
   1.4–1.9pt wider than the strand it sits under. This is what handles a busy
   wallpaper, where no single global choice works — the BenQ here scores 1.00 on
   variation, and its photograph is white stone in one place and near-black in
   the next. It is emphatically not the glow the brief rules out: no blur, no
   spread, no bloom; it is a crisp edge, the same trick as an outlined caption.

Measured on the four displays connected here: 0.87 and 0.77 luminance (light
treatment), 0.31 and 0.08 (the original bright ramps). Wallpapers are re-read on
a Space switch, a display change, and on the 60-second timer, because a rotating
wallpaper folder changes under you with no notification at all — which happened
mid-session on the BenQ.

## Motion

The brief's failure mode — a visible jump at the sample boundary — is a pixel
question, so it was answered in pixels. `sill --shift a.png b.png …` correlates
consecutive screenshots and reports how far the band actually moved. It
correlates on colour saturation, because on a photographic wallpaper plain
luminance just locks onto the (stationary) wallpaper texture.

- Mask-animated build, frames ~0.47s apart: **0px every time** — stepping.
- Current build, seven consecutive intervals ~0.47s apart: **+4px, +4px, +4px,
  +4px, +4px, +4px, +4px** (8.5px/s ≈ 4pt/s = one sample step per second).

Uniform fractional steps across every interval, including the ones that straddle
a sample boundary, is what "no visible jump" looks like numerically.

## Profiling, and two things that were costing more than the wave

Instruments is not installed, but macOS ships `sample`, which needs no Xcode.
Twenty seconds of it on the running app, and the hot path was not what I would
have guessed:

1. **Non-specialised generics.** Letting a band draw a slice of the shared
   history meant a generic `Curve.path`, and across a module boundary Swift
   cannot specialise that — every point access became a protocol-witness call
   with malloc traffic behind it. Building the paths inside `SillCore`
   (`Frame.paths`) put it back on the fast path.
2. **The screen-lock probe.** `CGSessionCopyCurrentDictionary` is an XPC
   round-trip to the window server, and it ran every second — half the
   remaining cost, more than drawing the wave. It now runs every five seconds.
   A screen that has just locked keeps sampling for a moment; nobody is
   looking at it.

Main-thread samples inside the timer callback, out of ~17,000: **102 → 50 →
26**. What is left is `CGPathAddCurveToPoint` — the wave itself.

## Performance

**Measured over 600-second windows, one band, on a machine in normal use:**

| Build | CPU | Memory |
| --- | --- | --- |
| Before profiling | 0.465% of one core | 13 MB |
| After profiling | **0.278% of one core** | 14 MB |

That is about 1.7 seconds of CPU per ten minutes. Four bands (one per display)
measured 0.663% before the same fixes; the per-band work is now shared, sliced
and skipped when occluded, so the multi-display case benefits most.

For scale: the nearest wallpaper-native competitor advertises "roughly 0% CPU
idle and under 100MB of RAM". Sill is 14 MB.

- Sampling suspends on occlusion, display sleep and screen lock
  (`SamplePlan`), slows 2x on battery and 4x in Low Power Mode.
- `Timer.tolerance` is 0.2s so the OS can coalesce the wakeups.
- The only per-sample work in the app is nine path rebuilds; everything between
  samples is Core Animation on the render server.

## The wave was being extruded from the wrong end

The band drew fifteen minutes of history it had never measured. `History` starts
full — a ring pre-seeded so the wave has something to draw — so a fresh launch
showed a dead-flat line at 0% CPU stretching back through time nobody watched,
with the real readings entering at one end. That is what "it builds downwards"
was: not motion, but a lie unspooling.

It now draws only what it measured. `History` counts real pushes (`filled`),
`Frame` carries that count, and the strand paths are clipped to it — and, since
index 0 is drawn at `along = 0` (the OLDEST end), they are also pushed down the
band by `(sampleCount - measured) * step` so the newest sample still sits at the
newest end and the gap is left where the missing time belongs. The panel's
"shown" figure is clamped the same way, and the hover readout cannot scrub into
the blank stretch.

**A sign I got wrong twice, and the measurement that settled it.** I decided
`scrollPerSample` was inverted and flipped it, reasoning that a sample's `along`
grows as it ages. It does not. Histories are oldest-first in a fixed ring drawn
from index 0, so when a reading arrives the oldest is dropped and every survivor
moves DOWN one index — one step closer to `along = 0`. The original sign was
right; my "fix" made the translation fight the redraw, which reads as a band
that shivers instead of drifting. It shipped that way in the first v1.0 disk
image, for about an hour.

What settled it was not more reasoning. Loading the machine hard for twelve
seconds and photographing the band puts the wide red strands at exactly one end,
and they were at the bottom: newest at the bottom of a vertical band, history
ageing upwards, `scrollPerSample` positive. The comments on both members now say
so, and the test asserts the invariant with an ageing — not a rejuvenating —
sample.

The band also sat on the wrong window level. `desktopIconWindow + 1` put it above
the icons on the desktop, so a strand crossed a file's name. The band is scenery:
`desktopIconWindow - 1` puts it under anything you actually keep on the desktop,
still above the wallpaper, still below every app window.

## Centred on the screen, not on the free space

The band was centred on `visibleFrame`, which excludes the menu bar. That puts it
half a menu bar (15pt here) off centre against everything else on the screen —
most visibly the Dock, which centres on the whole display. It now insets from the
visible frame on the edge it hugs, so it still clears the Dock and the menu bar,
but centres on `NSScreen.frame`, clamped so a full-length band can never be
pushed under the menu bar. `ScreenInfo` carries both rectangles for this.

## What the sweep covered

Every edge x three widths against computed geometry; all five ramps; all three
backgrounds; area fill; all twenty-five shape/fill metric pairs; five history
spans; both materials; dimming on and off — driven through `defaults` and
`--reload` on the running app, checking the window frame each time rather than
trusting that a setting was applied. Then, on the live band: the panel on all
four edges, the hover chevron, the scrub readout, Settings fitting without a
scroll bar, one band per display and a band pinned to a chosen display, the
first-run hint, and the disk and network samplers under real load (2.8 MB/s
write under `dd`, 3.1 MB/s down under `curl`).

Two apparent failures were the desk, not the app: a band under a window draws
nothing and suspends sampling, by design. `sill --exposed` was added to report
exactly how much of the band another window is covering, so that case stops
looking like a drawing bug.

## Second pass: what hostile numbers found

Feeding the core NaNs and infinities crashed it on the first call:
`Headroom.value` converts to `Int`, and `Int(nan)` traps. Every reading in
the panel and in the hover readout went through a conversion like that, so a
single division by a zero-length interval anywhere in a sampler would have
taken the app down. Measured values now round through a non-trapping helper,
and `History.push` refuses non-finite values outright — a NaN in the ring
becomes a NaN path coordinate, and Core Graphics then draws nothing at all
without so much as a warning.

Three more, all found by measuring rather than reading:

- **The wallpaper was re-decoded per band rectangle.** The backdrop cache is
  keyed on the rectangle, and decoding even a 512px proxy of a photograph
  costs 110ms here, on the main thread. Fifteen steps of the width slider
  cost 1.6s of work; they now cost 0.08s, because the decoded proxies are
  cached per wallpaper.
- **Switching the metric emptied the band.** Since histories are only kept
  for the two metrics being drawn, pointing the wave at another one handed it
  an empty history — which, now that the band only draws what it measured,
  means an empty band for a quarter of an hour. CPU, memory, network and disk
  are recorded from launch whether drawn or not (0.3ms a tick between them).
  GPU is not: its accelerator statistics cost 2ms a read, which at one a
  second would roughly double what Sill costs at rest.
- **The rate scale decayed per sample, not per second.** A band set to an
  hour of history takes a reading every twenty seconds, so its network scale
  stayed pinned to a download that had finished hours before.

Also: the open panel stops refreshing while it is not visible (the process
table is 2.5ms a tick, the GPU another 2ms), the window no longer extends
past the far edge of a small display, and the hover readout says nothing
when the pointer is over the stretch a young band has not drawn yet.

## Third pass: the scenario loop

A script that walks every combination the app offers — four edges by four
backgrounds, five ramps, all twenty-five shape/fill pairs, five history spans,
four widths, both materials, every display alone and all of them at once, and
an open/close on each edge — driving the running app through `defaults` and
`--reload` and checking the window geometry it actually produced against the
geometry the layout rules say it should have. Eight rounds: 1,416 checks, and
the only failures were the harness's own — it counted three displays where the
app had four, because the main one is starred in `--screens` output.

Two things the loop turned up that were not in the checks:

- **Settings costs 40MB and used to keep it.** The window holds a SwiftUI
  hierarchy; the app sat at 53MB after one visit and stayed there, against 14MB
  for the band alone. The controller is now released when the window closes.
- **The click catcher is a second window.** Worth stating: `--windows` now
  lists two desktop-level windows per band, and anything reading that output
  has to pick the lower one.

## Not verified, and why

- **The lock suspension itself.** The polling fix went in after the machine had
  already unlocked, and locking the user's screen again to prove it was not a
  reasonable thing to do mid-session. The probe is the documented API for it.
- **Left and bottom edges live, and ramps other than Load live.** Right and top
  were checked on the running app; all four edges x all five ramps are covered by
  the golden images, which exercise the same geometry and ramp code. By the time
  the remaining edges came up, the desktop was covered by the user's own windows
  — a desktop-level window is invisible under them by design.
- **The open/close animation mid-flight.** Both end states were captured; the
  intermediate frames were not, for the same reason. Both directions animate
  values (`animator()` on the panel, an explicit `CABasicAnimation` with from/to
  on the wave), which is what the brief asks for instead of a rebuilt view.
- **Hovering with a real pointer.** The hint was verified through a forced
  hover (`sill --hover`) and in the offscreen renderer, both directions, over the
  real wallpaper. Moving the pointer needs Accessibility permission.
- **Physically unplugging the chosen display.** The fallback and restore paths
  were exercised by pointing `displayUUID` at an absent display and back, and the
  logic is unit-tested against invented screen configurations
  (`ScreenSelectionTests`), but no cable was pulled.
- **A busy multi-coloured wallpaper.** Changing the desktop picture needs
  Automation permission this session does not have. Both materials were checked
  against the light wallpaper in use and against dark app windows.
- **Reduce Transparency / Reduce Motion as real system settings.** Toggling them
  needs access to protected preferences; both were exercised through the
  environment overrides, which feed the same code paths.
- **Click-through by actually clicking.** Moving the pointer requires Accessibility
  permission. The hit-testing rule (`ignoresMouseEvents` unless the pointer is
  inside the band, or inside the panel while open) is driven by a global
  mouse-moved monitor, which needs no permissions, but no synthetic click was
  made through the band.
- **Instruments.** Not installed; see above.
